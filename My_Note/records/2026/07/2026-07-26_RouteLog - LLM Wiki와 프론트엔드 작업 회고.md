# RouteLog - LLM Wiki와 프론트엔드 작업 회고

## 0. 다시 읽을 때 이것만 보기

### 한 줄 요약

RouteLog의 문서와 프론트엔드를 함께 정리하면서, 문서가 많아지는 것보다 각 문서의 역할과 검증 가능한 완료 기준을 분명히 하는 것이 더 중요하다는 점을 확인했다.

### 핵심 판단 3개

1. 현재 상태, 작업 결과, 장기 결정, 개인 회고는 서로 다른 문서에 기록해야 한다.
2. 자동 검증을 통과한 범위와 실제 기기에서 확인한 범위를 명확하게 구분해야 한다.
3. LLM Wiki는 프로젝트의 재사용 지식을 담고, My Notes는 작업 과정에서 얻은 나의 판단과 배움을 담아야 한다.

### 다음에 적용할 원칙 3개

1. 구현 전에 기준 문서와 완료 조건을 먼저 확정한다.
2. 검증하지 못한 항목은 완료로 포장하지 않고 차단 사유와 함께 남긴다.
3. 작업이 끝나면 변경 목록을 복사하지 말고, 다음 판단에 도움이 되는 배움만 My Notes에 남긴다.

### 다시 볼 필요가 있는 경우

- 프로젝트 문서가 서로 다른 현재 상태를 말하기 시작했을 때
- 로컬 자동 검증과 실제 기기 검증의 경계가 모호해졌을 때
- AI에게 대규모 문서 정리나 여러 TASK의 연속 수행을 맡길 때

## 2. 무엇을 했는가

### 2.1 프로젝트 문서의 역할을 분리했다

문서를 하나로 합치는 대신 각 문서가 답해야 하는 질문을 구분했다.

- `HANDOFF.md`: 지금 어떤 상태이며 바로 다음에 무엇을 확인해야 하는가
- `docs/task/`: 특정 작업에서 무엇을 변경하고 어떻게 검증했는가
- `docs/decisions/`: 왜 그 방향을 선택했는가
- `docs/source/`: 현재 구현과 계약을 이해하기 위한 기준 정보
- `My_Note/records/`: 이 작업을 통해 내가 무엇을 판단하고 배웠는가

이 구분을 통해 과거의 상세 HANDOFF가 현재 상태처럼 보이는 문제도 발견했다. 이후 과거 상세 기록은 보관 영역으로 옮기고, 루트 HANDOFF를 현재 상태의 단일 기준으로 삼았다.

### 2.2 프론트엔드의 완료 상태를 다시 확인했다

공통 API 타입과 인증, Feed, Detail, Record, Profile, My Routes, Bookmark 흐름을 점검했다. 단순히 화면이 존재하는지를 보는 것이 아니라 다음 기준을 중심으로 확인했다.

- Screen → Hook → Service → apiClient 흐름이 유지되는가
- 로딩, 빈 상태, 오류, 재시도가 구분되는가
- 중복 요청을 막는가
- 서버의 오류 코드와 페이지 응답을 잃지 않는가
- GPS 규칙이 문서와 코드에서 동일하게 적용되는가

이 과정에서 공통 비동기 상태 표현을 정리하고, 일부 목록의 오류와 빈 상태가 동시에 보이는 문제를 보완했다. GPS의 5m 이하 변화 무시 조건도 경계값을 포함하도록 맞췄다.

### 2.3 검증의 경계를 명확히 했다

TypeScript 검사와 백엔드 테스트는 통과했지만, Android 실제 기기에서의 OAuth, 지도, 위치 권한, 전체 사용자 흐름은 환경 부족으로 검증하지 못했다.

처음에는 구현 완료와 검증 완료를 하나의 상태로 다루기 쉬웠다. 그러나 실제로는 다음 세 가지가 다르다.

1. 코드가 작성되었다.
2. 로컬 자동 검증을 통과했다.
3. 실제 사용자 환경에서 동작을 확인했다.

이번 작업에서는 세 번째 단계가 남았다는 사실을 차단 사유와 함께 문서에 남겼다. 이것은 미완료를 숨기는 기록이 아니라, 다음 검증자가 어디서 시작해야 하는지를 알려주는 기록이다.

### 2.4 DB 문서는 변경하지 않고 감사했다

DB 문서 사이의 역할과 정합성을 점검했지만 SQL을 실행하거나 스키마를 변경하지 않았다. 문서 감사와 실제 마이그레이션은 권한과 위험도가 다른 작업이므로 분리해야 한다고 판단했다.

## 3. 어떤 판단을 했는가

### 3.1 확정한 판단

- 현재 상태를 전달하는 문서는 하나여야 한다.
- 과거 실행 결과는 현재 상태판이 아니라 TASK나 보관 문서에 남겨야 한다.
- 자동 테스트 통과는 실제 기기 검증을 대신하지 않는다.
- 문서 정합성 점검은 코드나 DB를 임의로 고치는 작업으로 확대하지 않는다.
- My Notes에는 파일 변경 목록보다 판단이 바뀐 지점과 재사용할 배움을 남긴다.

### 3.2 보류한 판단

- Android 실제 기기에서 OAuth와 GPS 흐름이 정상인지 여부
- 실제 Supabase 세션과 사용자 데이터가 모든 화면에서 기대대로 연결되는지 여부
- 문서 구조가 장기적으로도 현재 규모를 유지할 수 있는지 여부

이 항목들은 추측으로 결론 내리지 않고, 실제 환경이 준비되었을 때 다시 확인해야 한다.

---

## 4. 잘된 점

- 긴 작업을 TASK 단위로 나누어 구현과 검증 근거를 남겼다.
- 코드 변경이 금지된 범위와 문서 감사 범위를 구분했다.
- 환경변수의 실제 값을 읽거나 기록하지 않고 존재 여부만 다뤘다.
- 검증하지 못한 실제 기기 항목을 성공으로 표시하지 않았다.
- 문서 링크와 역할을 최종적으로 다시 감사하여 드리프트를 줄였다.

## 5. 아쉬웠던 점과 원인

### 5.1 문서 구조를 먼저 완전히 이해하지 못했다

처음 작성한 작업 기록을 프로젝트 루트의 `record/`에 두고 변경 결과를 장황하게 나열했다. 그러나 기존 원칙상 이 기록은 `My_Note/records/연도/월/` 아래에 있어야 하며, 단순 변경 로그가 아니라 작업 후의 판단과 배움을 담아야 했다.

원인은 파일 이름과 “record”라는 일반적인 의미만 보고, 이 저장소가 이미 정한 My Notes의 역할과 계층을 먼저 확인하지 않은 것이다.

### 5.2 결과 목록이 지나치게 구현 중심이었다

TASK별 변경 내용을 다시 나열하면 원본 TASK 문서와 중복된다. 시간이 지난 뒤 다시 읽을 때 중요한 것은 어느 파일을 고쳤는지가 아니라 다음과 같은 내용이다.

- 왜 문서 역할을 분리했는가
- 무엇을 완료로 간주하지 않았는가
- 다음에는 어떤 순서로 판단해야 하는가

### 5.3 활성 문서와 역사 기록의 경계가 늦게 정리됐다

루트 HANDOFF와 상세 HANDOFF가 동시에 존재하면서, 둘 다 현재 문서처럼 참조되는 문제가 있었다. 문서 구조를 설계할 때부터 “현재 상태의 단일 기준”을 먼저 정했어야 했다.

## 6. 배운 점

### 6.1 문서는 위치가 곧 의미다

같은 내용이라도 `docs/task/`, `docs/source/`, `docs/archive-or-legacy/`, `My_Note/records/` 중 어디에 놓이는지에 따라 독자가 기대하는 역할이 달라진다. 새 문서를 만들기 전에 비슷한 이름의 폴더가 아니라 실제 운영 원칙과 기존 문서 예시를 먼저 확인해야 한다.

### 6.2 완료 상태는 검증 수준을 포함해야 한다

“완료”라는 표현만으로는 부족하다. 로컬 타입 검사, 자동 테스트, 번들 생성, 실제 기기 검증은 서로 다른 증거다. 이후에는 결과를 기록할 때 검증 환경과 확인하지 못한 범위를 함께 남겨야 한다.

### 6.3 좋은 인수인계는 상세함보다 기준이 선명하다

모든 작업 이력을 HANDOFF에 넣으면 길어지지만 현재 상태는 더 불분명해진다. 현재 상태판은 짧게 유지하고, 상세 근거는 TASK와 보관 문서로 연결하는 편이 다음 작업자에게 더 유용하다.

### 6.4 AI가 만든 문서도 문서 체계의 독자다

AI는 지시가 없으면 내용을 잘 정리하더라도 잘못된 위치와 형식에 저장할 수 있다. 따라서 작업을 맡길 때 “무엇을 쓸 것인가”와 함께 “어떤 종류의 문서이며 무엇을 쓰지 않을 것인가”를 알려줘야 한다.

---

## 7. 다음에 적용할 원칙

1. 새 문서를 만들기 전에 해당 폴더의 원칙 문서와 기존 예시를 읽는다.
2. 현재 상태는 HANDOFF, 작업 증거는 TASK, 판단 이유는 decisions, 개인적 회고는 My Notes에 둔다.
3. My Notes에는 변경 파일 목록을 복제하지 않는다.
4. 자동 검증과 수동 검증을 별도 항목으로 기록한다.
5. 외부 환경 때문에 확인하지 못한 항목은 차단 사유와 재검증 조건을 함께 남긴다.
6. 장기적으로 반복 적용할 수 있는 내용만 LLM Wiki나 principles의 후보로 분리한다.

## 8. LLM Wiki / My Notes 연결

### 8.1 LLM Wiki에 남길 수 있는 일반 원칙

- 현재 상태 문서는 단일 기준을 가져야 한다.
- 작업 결과와 현재 상태, 장기 결정, 개인 회고는 역할별로 분리한다.
- 자동 테스트와 실제 환경 검증은 서로 대체할 수 없다.
- 보관 문서는 현재 운영 문서처럼 참조하지 않는다.

### 8.2 My Notes에 남길 개인적 고찰

- 나는 많은 문서를 만드는 것보다 각 문서를 다시 찾을 수 있고 역할을 즉시 이해할 수 있는 구조를 원한다.
- 작업 결과를 성실하게 나열하는 것만으로는 좋은 회고가 되지 않는다.
- 검증하지 못한 것을 솔직하게 남기는 기록이 다음 작업의 신뢰도를 높인다.
- AI에게 문서 작업을 맡길수록 기존 폴더의 의도와 문서 유형을 먼저 전달해야 한다.
