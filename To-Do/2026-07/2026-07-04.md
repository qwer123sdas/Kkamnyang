- Prompt

``` prompt

- Result
```
지금 프로젝트는 프론트 작업으로 넘어가는 시점이라 AI가 매번 전체 문서를 읽으면 토큰 낭비가 큽니다. 특히 docs/task가 이미 많고, 일부 문서는 인코딩이 깨져 보여서 AI가 잘못 해석할 위험도 있습니다.

  LLM WIKI는 “긴 문서 전체”를 대체하는 게 아니라, AI가 작업 시작 전에 읽을 압축된 맥락입니다.
  Graphifyd는 문서 간 관계를 명시해서 다음 질문에 빠르게 답하게 만드는 보조 레이어입니다.

  예를 들면 이런 관계를 만들 수 있습니다.

  RouteFeedScreen
  -> useRouteFeed
  -> routeService.getFeed
  -> GET /api/v1/routes/feed
  -> backend/api/route_api.py
  -> backend/services/route_service.py
  -> backend/repositories/route_repository.py
  -> docs/task/TASK-009-route-feed.md

  이 구조가 있으면 프론트 화면 수정 시 AI가 관련 파일과 문서를 빠르게 좁힐 수 있습니다.

  토큰량 측면에서는 장점이 큽니다.

  - 작업 시작 시 전체 문서 대신 00-LLM-ENTRY.md + 관련 map 문서만 읽으면 됨
  - 반복 설명 토큰 감소
  - AGENTS/계약/금지사항 누락 가능성 감소
  - 코드 탐색 범위 축소
  - 프론트 작업 시 Screen/Hook/Service/API 연결을 빠르게 파악 가능

  단점도 있습니다.

  - Wiki가 오래되면 오히려 AI가 낡은 정보를 믿을 수 있음
  - 문서와 코드가 불일치하면 Graph가 잘못된 방향을 줄 수 있음
  - 최초 구축 시 요약/링크 정리 비용이 있음
  - Graphifyd 산출물이 너무 상세하면 다시 토큰을 많이 씀

  그래서 핵심은 “짧은 진입점 + 화면/도메인별 얕은 지도 + 원문 링크”입니다. 문서 본문을 중복해서 길게 복사하면 안 됩니다.
```

- 기존 코드는 수정하지 않는다.

- 애매한 부분은 임의로 결정하지 말고 작업을 멈추고 질문한다.
    
- KKamyang 프로젝트의 기존 정책을 존중한다.
    
- Screen → Hook → Service → apiClient 구조 원칙을 문서에 명시한다.
    
- MVP 범위는 RUN 중심이며, 등산/라이딩 등 확장 기능은 후순위임을 문서에 명시한다.

## `docs/05-decisions.md`

프로젝트에서 AI가 임의로 바꾸면 안 되는 정책을 정리한다.

반드시 포함할 내용:
```markdown
# Decisions

## 아키텍처 정책

- Screen에서 직접 fetch하지 않는다.
- API 호출은 Service 계층을 통해서만 한다.
- 기본 구조는 Screen → Hook → Service → apiClient를 따른다.
- 비즈니스 로직은 Screen에 두지 않고 Hook/Service에 둔다.
- 타입 우선 설계를 유지한다.

## MVP 정책

- MVP에서는 RUN만 지원한다.
- 등산, 라이딩은 후순위이다.
- Naver OAuth, 댓글, Route Cluster, Route History, Nearby Route는 후순위이다.
- 안정화와 QA를 우선한다.

## 인증 정책

- 초기 로그인은 Google OAuth 중심이다.
- Supabase 세션을 사용한다.
- access token은 FastAPI 요청 시 Authorization Bearer로 전달한다.
- 서버는 Supabase access token을 검증한다.

## 사용자 정책

- users.user_id는 UUID PK를 사용한다.
- login_id는 최초 설정 후 변경할 수 없다.
- login_id는 중복될 수 없다.
- OAuth 최초 로그인 시 login_id는 null일 수 있다.

## DB 정책

- users 테이블의 PK는 UUID를 사용한다.
- 나머지 주요 테이블 PK는 bigint를 사용한다.
- audit 컬럼은 created_at, created_by, updated_at, updated_by를 사용한다.

## AI 작업 정책

- 모호한 요구사항은 임의로 결정하지 않는다.
- 기존 구조를 깨지 않는다.
- MVP 범위 밖 기능을 임의로 구현하지 않는다.
- 문서와 코드가 충돌하면 작업 전에 사용자에게 확인한다.
```

## `docs/09-graphify-guide.md`

graphify 운영 가이드를 작성한다.

포함할 내용:

- graphify는 코드/문서 관계를 그래프로 분석하기 위한 도구이다.
    
- Obsidian Graph View는 문서 링크 관계를 보여준다.
    
- graphify는 실제 코드, import, 함수 호출, 파일 의존성, 문서 관계를 분석한다.
    
- graphify 산출물은 `docs/graph/` 아래에 보관한다.
    
- 예시 산출물:
    
    - `docs/graph/GRAPH_REPORT.md`
        
    - `docs/graph/graph.json`
        
    - `docs/graph/graph.html`
        
- graphify 결과는 Codex 작업 전에 영향 범위를 파악하기 위한 참고 자료로 사용한다.
    

반드시 다음 설명을 포함한다.

```markdown
## Obsidian Graph View와 graphify의 차이

| 구분 | Obsidian Graph View | graphify |
|---|---|---|
| 대상 | Markdown 문서 링크 | 코드, 함수, 클래스, 문서, 파일 관계 |
| 관계 기준 | `[[문서 링크]]` | import, function call, AST, 문서 의미 |
| 목적 | 사람이 문서 관계를 탐색 | AI/개발자가 코드 영향 범위 분석 |
| 강점 | 지식 정리, 문서 탐색 | 코드 구조 분석, 리팩터링 지원 |
```

## `docs/graph/README.md`

# Graph

이 폴더는 graphify 또는 유사한 코드/문서 구조 분석 도구의 산출물을 보관한다.

## 목적

- 코드 호출 관계 확인
- 파일 의존성 확인
- 문서와 코드의 연결 관계 확인

## 예상 산출물

- GRAPH_REPORT.md
- graph.json
- graph.html

## 주의사항

- graphify 산출물이 매우 클 경우 Git 추적 여부를 별도로 판단한다.
- 자동 생성 파일은 직접 수정하지 않는다.
- 사람이 정리한 요약은 별도 Markdown으로 작성한다.
```

## Obsidian 운영 규칙

문서에 다음 원칙을 반영한다.

- Obsidian Vault는 프로젝트 루트 또는 `docs/` 폴더를 열어 사용한다.
    
- 기본 진입점은 `docs/00-index.md`이다.
    
- 문서 간 연결은 가능한 한 Obsidian Wiki Link 형식인 `[[문서명]]`을 사용한다.
    
- 파일 경로가 필요한 경우 코드 블록 또는 inline code로 정확히 적는다.
    
- AI에게 읽힐 문서는 제목, 목적, 현재 상태, 정책, 주의사항을 명확히 구분한다.
    

## 태그 정책

필요한 문서에는 YAML frontmatter를 추가한다.

예시:

```markdown
---
tags:
  - llm-wiki
  - obsidian
  - codex
---
```

권장 태그는 다음 정도로 제한한다.

```text
#decision
#error
#task
#api
#db
#frontend
#backend
#auth
#mvp
#codex
#llm-wiki
#graphify
#obsidian
```

단, 기존 문서에 frontmatter가 없다면 무리하게 모든 문서에 추가하지 말고, 새로 만드는 문서 중심으로만 적용한다.

## 7. 회고

- 프롬프트 원문만 남기면 나중에 의사결정 맥락을 파악하기 어렵다.
- Daily Note에는 질문보다 결정, 결과, 다음 작업을 남기는 편이 더 유용하다.
- 프로젝트 지식은 `docs/`에, 개인 작업 기록은 `To-Do/`에 두는 방식이 적절하다.


---

  HANDOFF.md
  = 다음 작업자가 지금 바로 이어받기 위한 현재 상태 요약

  docs/decisions/
  = 왜 그런 결정을 했는지 남기는 장기 의사결정 기록

  docs/todo/
  = 아직 해야 할 프로젝트 작업 목록

  To-Do/
  = 개인 작업 로그 / Daily Note
최종 권장 구조는 이겁니다.

  HANDOFF.md
  docs/decisions/
  = 장기 의사결정 원문

  docs/todo/
  = 프로젝트 TODO

  To-Do/
  = 개인 Daily Note

  즉, HANDOFF.md는 “문서의 대체재”가 아니라 “다음 사람이 봐야 할 첫 화면”입니다.

  2. 변경 내용

  맞습니다. 문서가 늘어나면 잘못 운영할 경우 토큰 사용량이 늘어납니다.
  하지만 구조를 잘 나누면 오히려 토큰 사용량은 줄어듭니다.

  핵심은 AI가 모든 문서를 읽게 하지 않고, 인덱스 → 요약 → 필요한 상세 문서만 읽게 만드는 것입니다.

  3. 변경 이유

  문서가 많아져도 토큰이 늘지 않게 하려면 역할이 중요합니다.

  HANDOFF.md
  = 1~2분 안에 읽는 현재 상태 요약

  docs/00-index.md
  = 문서 위치 지도

  docs/guide/*.md
  = 운영 규칙 요약

  docs/decisions/YYYY/YYYY-MM.md
  = 필요할 때만 읽는 상세 결정 로그

  docs/todo/current.md
  = 현재 남은 작업만 짧게

  To-Do/
  = 기본적으로 AI가 읽지 않음

  즉, Codex가 기본으로 읽는 문서는 이 정도면 됩니다.

  AGENTS.md
  HANDOFF.md
  docs/00-index.md
  관련 feature 문서 1개
  관련 task 문서 1개

  필요할 때만 추가로 읽습니다.

  docs/guide/05-decisions.md
  docs/decisions/2026/2026-07.md
  docs/todo/current.md
  docs/graph/*

  그래서 문서가 많아져도, AI에게 “전부 읽어라”라고 하지 않으면 토큰 사용량이 폭증하지 않습니다.
