## 2026-07-25 - source 원본 명세 현행화 기준

### 결정

`AGENTS.md`, 완료된 Task의 검증 결과, 실제 코드와 자동화 테스트를 기준으로 `docs/source/` 원본 명세를 현행화한다.
준비 또는 미검증 상태의 Task는 구현 완료 근거로 사용하지 않는다.
API 명세에는 `IMPLEMENTED`, `PLANNED`, `DEFERRED` 상태를 표시한다.

### 이유

기존 source 문서에는 프로젝트명, MVP 활동 유형, 댓글 범위, API 구현 상태와 디자인 문서 성격이 서로 다르게 기록되어 있었다.
문서의 계획과 현재 구현을 구분하지 않으면 이후 Task에서 존재하지 않는 API나 기능을 완료된 계약으로 오인할 수 있다.

### 영향

- 제품명은 `RouteLog`로 통일한다.
- 현재 MVP 활동 유형은 `RUN`만 허용한다.
- 댓글은 프로젝트 MVP에 포함하되 개별 Task의 제외 범위와 구분한다.
- `docs/source/api-spec.md`에서 구현 상태를 명시한다.
- `docs/source/design-system.md`는 RouteLog 확정본이 아닌 `REFERENCE`로 취급한다.
- TASK-030~038은 `docs/source/` 원문을 직접 참조한다.

## 2026-07-25 - guide와 source의 책임 분리

### 결정

`docs/guide/`는 작업자가 빠르게 확인할 현재 적용 요약, 문서 탐색 경로, 변경 절차를 관리한다.
`docs/source/`는 요구사항, 아키텍처, API, DB, 디자인 시스템의 상세 판단 기준을 관리한다.
동일한 상세 규칙은 두 영역에 복사하지 않고 guide에서 source 원문으로 연결한다.

### 이유

상세 정책을 guide와 source에서 동시에 관리하면 한쪽만 변경되어 서로 충돌할 수 있다.
guide를 짧은 작업 안내서로 유지하면 AI와 작업자가 필요한 원문만 선택해서 읽을 수 있다.

### 영향

- `docs/guide/01-overview.md`는 프로젝트 진입점과 범위 확인 절차를 관리한다.
- `docs/guide/02-architecture.md`는 계층 요약과 코드 탐색 절차를 관리한다.
- `docs/guide/03-api-spec.md`는 API 원문과 변경 절차를 안내한다.
- `docs/guide/04-db-schema.md`는 DB 원문과 변경 절차를 안내한다.
- 상세 값, 필드, 타입 및 계약은 관련 `docs/source/` 문서를 기준으로 판단한다.
- 2026-07-05 결정에서 guide가 관리하도록 한 MVP 및 계층 원칙은 guide에 현재 적용 요약으로 유지하되, 상세 정의는 source 원문을 따른다.

## 2026-07-04 - Obsidian / LLM WIKI 문서 운영 구조

### 결정

Obsidian과 LLM WIKI 관리는 `docs/` 중심으로 운영한다.
루트 문서는 `docs/INDEX.md`에서 링크로 참조한다.

### 이유

AI가 읽어야 하는 프로젝트 지식과 개인 작업 로그를 분리하기 위해서다.
문서가 늘어나더라도 Codex가 모든 문서를 읽지 않고 인덱스와 관련 문서만 따라가게 하기 위함이다.

### 영향

- `docs/INDEX.md`를 문서 진입점으로 사용한다.
- 운영 가이드는 `docs/guide/`에 둔다.
- 기존 원본 문서는 `docs/source/`에 둔다.
- 기능별 LLM WIKI 문서는 `docs/feature/`에 둔다.
- graphify 산출물은 `docs/graph/`에 둔다.
- 이전 진입 문서 또는 중복 색인은 `docs/archive-or-legacy/`에 보관한다.

## 2026-07-05 - DEC 문서 제거 및 결정 기록 단순화

### 결정

`docs/decision/DEC-*.md` 독립 문서는 더 이상 사용하지 않는다.
기존 DEC-001의 프론트엔드 계층 원칙은 `docs/guide/02-architecture.md`에서 관리한다.
기존 DEC-002의 MVP 범위 원칙은 `docs/guide/01-overview.md`와 `docs/guide/05-decisions.md`에서 관리한다.

### 이유

작업 단위 판단은 `docs/task/TASK-*.md`에 있고, 장기 결정 배경은 월별 결정 로그에 기록한다.
별도 `docs/decision` 폴더를 유지하면 결정 진입점이 늘어나고, 현재 적용 기준을 판단하기 어렵다.

### 영향

- 신규 결정은 기본적으로 `docs/decisions/YYYY/YYYY-MM.md`에 기록한다.
- 현재 지켜야 할 요약은 `docs/guide/05-decisions.md`에서 확인한다.
- 확정 정책은 관련 `docs/guide/` 문서에 반영한다.
- `docs/decision/` 폴더와 기존 `DEC-*` 문서를 제거한다.

## 2026-07-04 - HANDOFF와 decisions 역할 분리

### 결정

`HANDOFF.md`는 현재 상태, 다음 작업, 주의사항, 주요 링크만 담는 짧은 상태판으로 유지한다.
상세 의사결정은 `docs/decisions/YYYY/YYYY-MM.md`에 기록한다.

### 이유

`HANDOFF.md`가 길어지면 다음 작업자가 핵심 상태를 빠르게 파악하기 어렵다.
결정 배경은 장기 기록으로 남겨야 하지만, 매 작업 시작 시 모두 읽을 필요는 없다.

### 영향

- Codex 작업 시작 시 `HANDOFF.md`를 먼저 읽는다.
- 상세 결정이 필요할 때만 `docs/guide/05-decisions.md`와 월별 결정 로그를 따라간다.
- `docs/guide/05-decisions.md`는 의사결정 본문이 아니라 인덱스로 유지한다.

## 2026-07-04 - current.md 생성 보류

### 결정

현재는 `docs/todo/current.md`를 만들지 않는다.
프론트엔드 작업 관리는 `docs/FRONTEND-BOARD.md`를 사용한다.

### 이유

현재 구조에서는 `docs/FRONTEND-BOARD.md`가 대기, 준비, 진행 중, 검증, 완료, 차단 상태를 이미 관리한다.
`current.md`를 추가하면 같은 내용을 복사하는 중복 문서가 될 가능성이 높다.

### 영향

- 백엔드, 문서, QA, graphify까지 포함하는 프로젝트 전체 TODO 허브가 필요해질 때만 `docs/todo/current.md`를 추가한다.

## 2026-07-04 - 개인 작업 로그와 프로젝트 지식 분리

### 결정

개인 작업 로그와 AI 대화 흐름은 프로젝트 지식 문서에서 링크하지 않는다.
프로젝트 지식, 운영 규칙, 결정, Task는 `docs/`에 남긴다.

### 이유

개인 로그가 LLM WIKI에 직접 연결되면 AI가 프로젝트 기준 정보와 개인 기록을 혼동할 수 있다.
개인 로그는 사용자가 명시적으로 요청한 경우에만 별도로 확인한다.

### 영향

- 프로젝트 지식 문서에서는 개인 작업 로그로 향하는 링크를 만들지 않는다.
- 장기 결정은 `docs/decisions/YYYY/YYYY-MM.md`로 승격한다.
- 확정 작업은 `docs/task/TASK-*.md`로 관리한다.
